# S-04 — One status enum, and the paper's closed-world asymmetries

Status: accepted (2026-10-04) · Gate: G0 (blocks G1) · Lane: A · Related: S-08, S-10

## Context

**Design v0.3.** Prose: "exactly one kernel status: `established`, `unresolved`, `unknown`", then adds `established_empty` and `established_false`. The `Segment` schema lists five. The paper also uses `possible` (yes/no slots).

**Deposited code (`revise_stream/gold.py`).** Reading the value and yes/no gold gives a *more irregular* picture than the proposal's S-4 describes:

- Value slots return `established | unresolved | unknown`. A **single-valued** key with no evidence yields candidate `{∅}`, normalised to `None`, hence `unknown`.
- A **multi-valued** key with no evidence yields `{∅}` normalised to `[]`. `_value_gold` only checks `alts[0] is None`, so the answer is **`established` with assertion `[]`**: closed-world "empty set" without any declaration.
- Yes/no `holds` slots: absence ⇒ `p["value"] in c` is false in every world ⇒ **`established`, assertion `False`** (closed-world negation).
- Yes/no mixed truth ⇒ `possible`. `possible` never occurs on value slots.
- `reported` is always `established` with the id map.

So the paper's closed world is applied **per slot type and per cardinality**, not uniformly. The design's compat statement "`completeness: declared(all)` on every frozen key" is too coarse: it would turn single-valued absence into `established_empty`/`established_false`, which the oracle answers `unknown`.

## Options

A. **Five-value `kernel_status` + adapter-computed `possible`.** `established | unresolved | unknown | established_empty | established_false`. `possible` is a v1 *slot-level* answer, produced by the adapter when a yes/no query has candidates both containing and not containing the value.
B. Three values plus `empty`/`false` as flags on `established`. Cleaner enum, but loses the "negative claim keeps its content" property in `Candidate`.
C. Add `possible` to the v2 enum. Rejected: it is a query-form artefact, not a property of a segment.

## Recommendation

**A.** Fix the prose to list five statuses. Define the compat profile **per key class**, not as a blanket `declared(all)`:

| Frozen key situation | v2 (profile `revise-stream-v1`) | v1 answer |
|---|---|---|
| single-valued, no evidence | `unknown` | `unknown` |
| multi-valued, no evidence | `established_empty` | `established`, `[]` |
| yes/no `holds`, no evidence | `established_false` | `established`, `false` |
| yes/no, mixed | `unresolved` | `possible` |

## Effect on `revise-stream-v1` and G1

Required for G1: without the per-class table the adapter cannot reproduce the 40,030 answers. The table is a deliverable of T-E3.

## Fixtures implied

- `fx-S04-single-no-evidence-unknown`, `fx-S04-multi-no-evidence-established-empty-profile-only` (open-world: `unknown`).
- `fx-S04-yesno-absence-false-profile-only`.
- `fx-S04-yesno-possible-roundtrip`: v2 unresolved projects to v1 `possible`.
- `fx-S04-unresolved-includes-empty-candidate`: single-valued key with alternatives `{A, ∅}` keeps the `empty` candidate.

## Open questions

1. Is the open-world product answer for a *multi-valued key with no evidence* `unknown` (recommended) even though the paper's oracle says `established []`? This is the single most visible difference between profile and product.
2. Should `established_empty` exist for single-valued keys ("explicitly has no employer")? Recommend yes, via `enumeration([])`-style negative evidence only.

### Decision (author, 2026-10-04): accepted
Per-slot-type compat profile. `declared(all)` was shorthand; the paper's conventions are per slot type (multi-valued slot with no justified member → `established_empty`; a never-asserted yes/no proposition → `established_false`; an undeclared single-valued slot → `unknown`), so the profile expresses them that way to be exact. `possible` is an adapter-only status. **The product default stays `open` everywhere.**

### Decision (author, 2026-10-05): negative evidence in the open-world product kernel (ruling 4, with the ruling-11 status for compatible denials)

* **Two compatible `not_value` candidates** (denials of different values): `kernel_status: unknown`, with **both negatives listed as constraints in `alternatives`** (the value is narrowed, not determined). **`established_false` only when completeness makes them exhaustive.**
* **Positive + negative on the same value over overlapping valid time = `unresolved`**, both readings as candidates (design v0.3).
* The compat profile keeps rejecting what the oracle cannot represent.

Implemented by `palimem.kernel.polarity` (product profile only; docs/KERNEL.md "Negative evidence"), under the semantics stated in its module docstring: a denial and an affirmation of the same value conflict, everything else is compatible; interpretations are the consistent TRUE/ERR labellings in which every ERR report is disputed by a TRUE one. Statuses: only denials: one denied value is `established_false` (design v0.3: explicit negative evidence suffices), two or more are `unknown` with all listed; positive evidence with no denial of it: `established` (denials of other values are consistent constraints, not listed); positive and a denial of the same value: `unresolved` (`value(v)` and `not_value(v)`; for a set, `set(...)` with and without `v`, the negative reading standing for an otherwise empty set).

**Contract consequence (additive in effect, flagged):** a `Segment` of status `unknown` may now carry `alternatives`, but only *negative* candidates (constraints); it still names no established candidate. `Segment.__post_init__` and the generated `Segment` JSON Schema changed accordingly (`schemas/*.schema.json`), and `decide()` passes the constraints through to `Resolved.alternatives` on an `unknown` answer. No field was added or removed.

**Scope (checked; outside it the kernel raises `KernelUnsupported`, never guesses):** `assert` cues only on a key that has a denial (no `change` / `correct`), no `valid_from` / `valid_to` (staged, S-09: evidence beside a denial is read as claims about the key now), a single-valued key with at most one distinct positive value, a set-valued key with at most one member both affirmed and denied.

**Not implemented, flagged for the author:** the ruling's clause "`established_false` only when completeness makes them exhaustive" has no completeness plumbing in the kernel's `AttrSpec`, and a `Segment` carries one established candidate, so several compatible denials are `unknown` under every completeness mode (including `declared`). Also: the status of a denial beside *competing* positive values, and denials with valid-time intervals, are open.

Evidence: `tests/test_negative_evidence.py` checks the kernel against an **independent brute-force reference** (enumerates every TRUE/ERR labelling and reads the status off the admissible worlds) on 600 random cases (shape distribution: unresolved, established, established_false, unknown in both single- and set-valued keys); the comparison is mutation-sensitive (a reference with "nothing conflicts" disagrees on 231 of 600). `tests/test_negative_evidence_memory.py` runs the whole pipeline on both backends; conformance rows 13a, 13b and 18 (now `unknown`, per this ruling) and `r04-*` pass.
