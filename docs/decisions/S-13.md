# S-13 — Tombstone contents versus the right to erasure

Status: proposed · Gate: G0 · Lane: A · Related: T-C8, T-H4

## Context

**Design v0.3.** Deletion removes content, raw reference and materialised values derived only from the report, but "leaves a tombstone with the report id, key, actor and reason so the cascade remains explainable", and "states which historical answers can no longer be reconstructed".

**Deposited code.** No deletion concept exists; retraction is a belief operation and the log keeps everything. This is entirely new behaviour with no oracle.

**The problem.** The tombstone's own fields can be personal or sensitive data: `key = (alice, health_condition)` reveals the subject and category even with the value removed; `actor` may identify a person; a free-text `reason` may repeat the content; ULIDs embed a timestamp. Hashing `key` naively is a low-entropy dictionary problem (entities × attributes is a small space).

## Options

A. **Minimal pseudonymised tombstone (recommended).**
   ```
   Tombstone { report_id, entry_hash (original, if the backend has the chain),
               key_ref = HMAC(store_secret, key), actor_ref = pseudonymous principal id,
               reason_class: erasure_request | legal_hold_release | retention_expiry | other,
               erased_at, affected_versions: [(key_ref, belief_version)] }
   ```
   No free text, no plain key, no value. `store_secret` is held outside the data tables (host-supplied).
B. Full tombstone as designed (key, actor, reason). Simple, but may itself be personal data.
C. No tombstone, only a count. Cascade becomes unexplainable; "which historical answers are unreconstructable" cannot be stated.

## Recommendation

**A.** `affected_versions` is the answer to "which historical answers can no longer be reconstructed": every belief version whose pinned set included the report is flagged `reconstructable: false` for queries at those versions. Deletion triggers the same dependency repair as withdrawal. Backups: a documented procedure (retention window, restore-then-re-apply-tombstones) is required; crypto-shredding is an open research item, not a v1 promise. Legal review of the claims is a gate (T-H4); until then documentation says "designed to support" not "compliant".

### Amendment (author decision, 2026-10-04): the hash chain and tombstones

The evidence log carries a hash chain as a **storage-layer property**: `prev_hash` and `entry_hash` live on the log *row*, salted (per-row salt) so contents cannot be confirmed by guessing. They are **not** Report fields, so the Report contract and G0 fixtures are unchanged. `verify_log(from, to)` is an optional-capability backend operation; the SQLite default includes the chain.

Consequences for deletion:

- A tombstone **preserves the chain**: the row stays, `prev_hash` is untouched, and the tombstone carries the **original `entry_hash`**. The next row's `prev_hash` therefore still links, and `verify_log` passes across a tombstone.
- The **per-row salt is erased with the content**. If the salt survived, `entry_hash` plus salt would allow confirming a guessed content, defeating the erasure.
- A tombstoned row's content hash can no longer be re-verified; `verify_log` reports such rows as `linked: true, content_verified: false` rather than failing.
- Tombstone gains `entry_hash` (original). It still carries no plain key, value or free text.
- A backend without the chain remains conformant; its tombstones simply omit `entry_hash`.

## Effect on `revise-stream-v1` and G1

None: the paper has no deletion. Deletion is exercised only by independent fixtures.

## Open questions

1. Is the `store_secret` rotation policy needed (rotating breaks key_ref linkage across tombstones)? Recommend: no rotation in v1; document.
2. Should a tombstone expire? Keeping it forever sustains explainability, but may conflict with minimisation. Needs the T-H4 reviewer's view.
3. Does the extractor stamp (model, prompt hash) of an erased report remain? Recommend yes; it is not personal data by itself.
