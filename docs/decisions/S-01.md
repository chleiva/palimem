# S-01 — The `confirm` cue versus derived confirmation

Status: accepted* (2026-10-04) · Gate: G0 · Lane: A · Related: S-02, S-03, S-11

## Context

**Design v0.3.** `Report.cue` includes `confirm`, and the Admission model also *derives* confirmation: a quarantined source's report becomes admissible when "an already admissible report from a different `origin_group` with the same key and an equivalent proposition" exists. Nothing says what an explicit `confirm` cue does or whether it can corroborate.

**Deposited code.** There is no confirm operation. `Observation.op_cue ∈ {none, change, correction}` (`revise_stream/model.py`). The only corroboration notion is `Stream.corroborated(o, tau)`: same key, same value, an admitted observation from a *different origin*. It is **derived**, never emitted, and it only affects admissibility under the P1 sensitivity variant (`oracle_v1._key_interps`, `policy == "P1"`) and the support model's origin grouping (`palimpsest/support.py`). Under the main configuration (P0c / P0cSU) corroboration changes nothing about admissibility.

So the paper gives no precedent for a source-emitted `confirm`, and in the SDK the *only* place confirmation matters is quarantine (new).

## Options

A. **Remove `confirm` from the cue enum.** Confirmation is always derived from equivalent `assert` reports of another origin group. An extractor turns "the wire also says X" into an ordinary `assert`.
B. **Keep `confirm` as an explicit endorsement** that must carry `target` (the report it endorses) and counts only if its own source is admissible and in a different origin group from the target.
C. Keep both, with `confirm` as syntactic sugar rewritten to an equivalent `assert` at append time.

## Recommendation

**A.** A source- or LLM-emitted `confirm` is an additional path to forge corroboration, and corroboration is the only way out of quarantine. Deriving it from equivalent asserts keeps one rule and one attack surface. Define "equivalent proposition" normatively in the same record set: equality after value normalisation, with `member(v)` ≡ `enumeration` containing only evidence for `v` explicitly *not* equivalent (an enumeration closes the world, a member does not).

## Effect on `revise-stream-v1` and G1

None. No frozen stream contains a confirm operation; the profile has no quarantined sources (see S-03), so derived confirmation never fires. G1 is unaffected, provided the profile pins `quarantine: none`.

## Fixtures implied

- `fx-S01-confirm-by-equivalent-assert`: quarantined report R1 plus an admissible equivalent assert from another origin group → R1 admissible, admission record cites the confirming report id.
- `fx-S01-same-origin-group-no-confirm`: second equivalent report from the *same* origin group → R1 stays quarantined.
- `fx-S01-confirm-cue-rejected`: a report with `cue: confirm` fails schema validation (under A).
- `fx-S01-agent-origin-never-confirms`: `agent_hypothesis` equivalent report → no confirmation.
- `fx-S01-member-vs-enumeration-not-equivalent`.

## Open questions

1. Does confirmation need to be *transitively* admissible (a report admitted by confirmation can itself confirm a third)? Design text says confirmation requires evidence "the system already trusts"; recommend: yes, but only reports admissible on their own merits (not by confirmation) count as confirmers, to avoid chain-laundering.
2. Should P1 (class-prioritised dispute, which uses corroboration) exist in the SDK at all? Recommend no: quarantine+confirmation replaces it; keep P1 only inside the harness for the study's sensitivity run.
